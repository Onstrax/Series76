# Texto de inicio para Kiro (copiar solo después de autorización del usuario)

Trabajaremos en el assessment "Series 76 Technical Assistant" de Konecto. Antes de generar código, lee el paquete `Series76_Kiro_Handoff_v1.0` completo, comenzando por `00_START_HERE/README_HANDOFF.md` y `01_CANONICAL_F0_F6/F6_kiro_master_alignment_v1.0.md`. Lee los tres PDFs originales; el PDF eléctrico es la única fuente de cifras técnicas, y el assessment define los requisitos mínimos. Examina a continuación los **siete dossiers canónicos F0–F6** y usa referencias históricas solo cuando necesites comprender decisiones.

Este material es **alineación, no tus Specs**. Construye en Kiro tus propias Requirements, Design y Tasks con criterios de aceptación y trazabilidad hasta las 35 historias, 15 QA y contratos de las fases. Documenta las alternativas importantes que encuentres, la escogida y la justificación; respeta las decisiones explícitas ya aprobadas. Distingue claramente requisitos del assessment, funcionalidades adicionales aprobadas, detalles técnicos delegados y resultados que requieren experimentación.

Prioriza requisitos evaluables y compromisos P0: FastAPI, LangChain con al menos un tool custom SQL, PostgreSQL Docker Compose, ingesta real del PDF con datos verificables, contexto multi-turn persistente, POST `/api/conversation` con `session_id` opcional y `answer`, app Android nativa de tres pantallas, Developer Debug protegido, datos visuales estructurados, backend/Android reproducibles y README completo. También fueron aprobados auth/register (solo user), tokens opacos, cifrado AES-256-GCM, jobs duraderos, confirmación condicional, caché protegido, y UX offline que advierte claramente y **deshabilita Enviar hasta reconectar** sin autoenviar borradores.

Diseño adoptado: monolito modular Feature-First + hexagonal ligera en backend, Repository/UoW/DTOs sin DAO redundante, ETL Pipe-and-Filter, agente y jobs como máquinas de estados, Android MVVM/UDF Feature-First. Tools especializadas (B) como candidata, comparar empíricamente contra genérica (A). Al menos dos candidatos OpenRouter por función LLM; controla gasto global: USD 10 hard limit, máximo USD 6 para desarrollo/evals, reserva de USD 4. No inventes números, no confíes en OCR/modelos para compatibilidad, verifica 100 % de la primera edición con PDF, no relajes AES-256-GCM silenciosamente.

Implementa por slices verificables cuando se autorice: contratos y datos, herramientas/agente, API/auth/persistencia/jobs/crypto, Android, evaluación y reproducibilidad. Cada slice debe incluir tests y evidencia. Para incompatibilidades reales de las decisiones aprobadas (fuente numérica, cifrado, permisos, contratos, UX), informa alternativas y pide aprobación del usuario. No generes conclusiones de test ni resultados de benchmarks que no se hayan ejecutado. No subas claves ni secretos al repo. Documenta tu configuración real de Kiro en su directorio de proyecto.
