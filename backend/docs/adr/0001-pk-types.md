# ADR 0001: Primary-key types for the catalog/provenance/ingestion/publication schemas

- Status: Accepted
- Date: 2025 (Spec 1 implementation)
- Deciders: data-and-ingestion implementation
- Related: `design.md` § "PK type — [DELEGATED] recommendation", Req 11.1, 11.4, 11.5

## Context

The design delegates the concrete primary-key type to implementation while
requiring that composite foreign keys use `(edition_id, parent_id)` to prevent
cross-edition references, and that `edition_id` be a stable, system-portable
identifier.

Two candidate strategies were considered:

1. **`BIGINT` generated-by-default-as-identity** internal PKs, with `edition_id`
   modeled as a `UUID`.
2. **`UUID` everywhere.**

## Decision

- Internal surrogate PKs for catalog, provenance, ingestion, and publication
  tables are **`BIGINT GENERATED BY DEFAULT AS IDENTITY`**. They are compact,
  index-friendly, and natural at the 68-row scale; auto-increment identity
  avoids client-side key generation and keeps composite FKs small.
- **`edition_id` is a `UUID`.** An edition identifier must be stable across
  systems (golden dataset binding, manifest references, replay reproduction),
  so it is not an auto-increment surrogate. It is supplied by the application
  (e.g. `uuid4`) at edition-creation time.
- `manifest_digest` is a **content hash** (stored as `TEXT`), not a primary key;
  it carries a `UNIQUE` constraint on `catalog_edition`.
- Composite foreign keys use `(edition_id, parent_id)` against an auxiliary
  `UNIQUE(edition_id, parent_id)` on the parent, so a child can never reference
  a parent belonging to a different edition.
- Pure link/bridge tables (`supply_profile_mode`, `source_cell_row_coverage`,
  `source_note_row_scope`) use **composite natural PKs** over their member
  columns rather than a surrogate, because the pair *is* the identity.
- `publication.catalog_current` uses a **constant single-value PK column**
  (`pin BOOLEAN PRIMARY KEY` with `CHECK (pin IS TRUE)`) so at most one active
  pointer row can ever exist.

## Consequences

- Joins and composite FKs stay compact and fast.
- `edition_id` can be referenced by other specs and artifacts without leaking a
  database sequence value.
- Mixing `BIGINT` surrogates with a `UUID` `edition_id` is a deliberate,
  documented split; any future change to this policy requires a new ADR.
